"""
ANALYSIS: rack.db vs searchRack.db - Is the duplication worth it?
===================================================================

YOUR CONCERN:
-------------
"Is there a benefit or reason to have rack.db AND searchRack.db? 
It seems to only cause issues. My initial thought was to have it as 
a security measure so changing things wouldn't accidentally delete 
items from my inventory (rack.db)."

CURRENT ARCHITECTURE:
--------------------
┌─────────────┐
│   rack.db   │ ← "Master" inventory (barcode scans go here first)
└──────┬──────┘
       │ updateSearchRackDB() syncs ↓
┌──────▼──────────┐
│ searchRack.db   │ ← "Search view" (enriched with titles from eBay/BOL/Amazon)
└─────────────────┘

WHAT EACH DATABASE DOES:
------------------------

rack.db (INVENTORY table):
- Stores physical location data from barcode scans
- Columns: BARCODE, ITEM_POSITION, PICTUREPOSITION, IMAGES
- Updated when you scan items to locations
- "Source of truth" for what's physically where

searchRack.db (SEARCHRACK table):
- Copy of rack.db + enriched data
- Columns: BARCODE, ITEM_POSITION, TITLE, ITEMID, QUANTITY, IMAGE, etc.
- Enriched by looking up barcodes in ebayStore.db, bol.db, amazonStore.db
- Used for the /searchrack UI search functionality

PROBLEMS WITH CURRENT DESIGN:
------------------------------

1. ❌ SYNCHRONIZATION ISSUES
   - Two copies of the same data that can get out of sync
   - updateSearchRackDB() DELETES everything and rebuilds from scratch
   - Causes issues like the 21 orphaned items on Oct 31
   - Every barcode scan writes to BOTH databases

2. ❌ COMPLEXITY
   - Every location update must update TWO places
   - Shelf operations must update BOTH databases
   - More code = more bugs
   - Harder to maintain

3. ❌ PERFORMANCE
   - updateSearchRackDB() is slow (deletes + rebuilds entire table)
   - Duplicate writes on every barcode scan
   - More disk I/O

4. ❌ DATA INTEGRITY RISKS
   - If one update fails, you have inconsistent data
   - CREATED_AT timestamps get lost on rebuild
   - Enrichment data can become stale

5. ❌ YOUR SECURITY GOAL ISN'T MET
   - searchRack.db is completely rebuilt from rack.db
   - So it offers NO protection - if rack.db is deleted, searchRack can't help
   - Both are in the same directory, same risk level

BETTER ALTERNATIVES:
-------------------

OPTION 1: SINGLE DATABASE WITH BACKUP (RECOMMENDED)
────────────────────────────────────────────────────
Use ONLY searchRack.db for everything:
- Store all data in one place (barcode, position, enrichment)
- Create automated daily backups (searchRack.db.backup-YYYYMMDD)
- Use deleted.db for "undo" functionality (already exists!)
- Much simpler, faster, more reliable

Benefits:
✅ No sync issues
✅ Simpler code
✅ Faster operations  
✅ Better security (automated backups)
✅ No data duplication

OPTION 2: VIEWS INSTEAD OF DUPLICATE TABLE
───────────────────────────────────────────
Keep rack.db as lightweight storage, but use SQL VIEWS for enrichment:
- rack.db stores locations only
- Create views that JOIN with ebayStore, bol, amazon for enrichment
- No duplicate data, always fresh

Benefits:
✅ No sync needed
✅ Always up-to-date enrichment
✅ True separation of concerns

Drawbacks:
⚠️ Slightly slower queries (JOINs on every search)
⚠️ More complex SQL

OPTION 3: SINGLE SOURCE WITH MATERIALIZED VIEW
───────────────────────────────────────────────
Use rack.db as master, create searchRack as a "cache":
- Only rebuild searchRack when enrichment data changes
- Use triggers or timestamps to know when to refresh
- Don't rebuild on every sync

Benefits:
✅ Faster than views
✅ Still separates concerns

Drawbacks:
⚠️ Still has sync complexity
⚠️ Not much better than current situation

MY RECOMMENDATION:
------------------
🎯 GO WITH OPTION 1: Single Database + Automated Backups

Here's why:
1. Your security goal is better served by backups than duplication
2. Much simpler codebase = fewer bugs
3. No sync issues ever again
4. You already have deleted.db for undo functionality
5. Can implement hourly/daily backups easily

Implementation Plan:
1. Migrate rack.db data into searchRack.db (merge tables)
2. Remove all updateSearchRackDB() calls
3. Update barcode scanning to only write to searchRack.db
4. Add automated backup script (run daily)
5. Keep deleted.db for undo functionality
6. Delete rack.db

SECURITY COMPARISON:
-------------------
Current Setup:
- rack.db and searchRack.db in same folder
- Both vulnerable to same accidental deletion
- searchRack gets DELETED and rebuilt regularly anyway
- No backup strategy
Security Level: ⭐⭐ (2/5)

Proposed Setup:
- Single searchRack.db as source of truth
- Automated daily backups to backups/ folder
- deleted.db for undo/recovery
- Optional: backups to cloud/network drive
Security Level: ⭐⭐⭐⭐ (4/5)

CONCLUSION:
-----------
The current two-database architecture is causing more problems than it solves.
Your original security goal is NOT being met - you need backups, not duplication.

RECOMMENDATION: Consolidate to single database + implement proper backups.
